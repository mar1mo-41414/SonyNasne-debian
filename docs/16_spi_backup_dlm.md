# 16. SPIフラッシュを「読むだけ」でバックアップする `.dlm`(と、バックアップへ戻す `.dlm`)

> **層**: 【OFW】 公式の起動経路で動く `.dlm`。旧・新のカーネルとは独立に使えます。

> 基板のSPIフラッシュ(ブートローダ・カーネル・RFS・NV領域)を、**書き込まず・Debianも入れず**、nasne自身に読み出させてHDDに置く方法です。
> はんだ付けやSPIライタ(CH341A等)は要りません。[docs/13](13_full_setup_from_official_hdd.md) のようにSPIを書き換える前の保険や、ブートローダ類の保存に使えます。
> 公式HDDの `00550066.dlm` を1ファイル差し替える仕組みは docs/13 と同じです。自己責任でお願いします。

## 何をするか

`make_stage1_dlm.py --mode backup` は、公式の `rcS` の最後(公式アプリを起動する直前)に、次の処理だけを挿し込んだ `.dlm` を作ります。

1. `/dev/mtd0`(SPIの先頭13MB: ブートローダ・カーネル・RFSなど)と `/dev/mtd1`(NV領域、3MB弱)を `dd` で**読むだけ**。書き込み・消去はしません。
   `mtd0` は2回読んで一致を確認します(`mtd1` は稼働中のjffs2なので2回目の比較は参考)。
2. 結果を、HDDの **sys1(既定)** または p3 の `/spi_backup/` に置きます(`--dest sys1|p3|both`)。
   `spi_mtd0.bin` / `spi_mtd1_nv.bin` / `MD5SUMS` / `SHA1SUMS` / `README.txt` / `backup.log`
3. そのあと、**公式アプリを普通に起動**します。

安全のため: すでに `/spi_backup/spi_mtd0.bin` があれば何もしません(SPIの内容が変わっていても上書きしません。取り直すときはそのディレクトリを消します)。
サイズ不一致・空き不足・マウント失敗などの場合は、バックアップを飛ばして公式の起動へ進みます。

## 手順

```bash
# 1. そのHDDの 00550066.dlm から、バックアップ版を作る(PC側。root不要)
python3 scripts/stage1/make_stage1_dlm.py build --official <HDDのsys1にある00550066.dlm> --out spi_backup.dlm --mode backup
# 2. HDDをPCにつなぎ、sys1をマウントして差し替える(元のファイルは退避される)
sudo mount /dev/sdX1 /mnt/nasne_sys1
sudo bash scripts/stage1/install_dlm.sh /mnt/nasne_sys1 spi_backup.dlm --backup-dir ./backup_sys1
sudo umount /mnt/nasne_sys1
```

3. HDDをnasneに挿して電源を入れる。**起動は約80秒遅れます**(読み出し中。基板のウォッチドッグ333秒には収まります)。公式アプリが起動したら完了です。
4. 電源を切り、HDDをPCに戻して `sys1` の `/spi_backup/` を取り出す。**そのあと `00550066.dlm` を元に戻してください**(`--backup-dir` に退避された `00550066.dlm.orig` を、同じ `install_dlm.sh` で書き戻す)。
   戻さなくても、次回からは「作成済み」でスキップするだけで害はありません。

`install_dlm.sh` は、新旧のヘッダ(ハードウェア種別・日付)が一致することを確認します。**`--official` には、そのHDD自身の `00550066.dlm` を渡してください**(別のバージョンのものだと拒否されます)。

## 注意・限界

- SPIの最後の64KB(`0xff0000` 以降)は、MTDとして見えないため含まれません。
- NV領域(`spi_mtd1_nv.bin`)は稼働中のファイルシステムを生で読むので、ファイルとしての整合は保証しません(設定の控えとして)。
- 公式の `busybox`(1.13.3)に `sha256sum` が無いため、同梱のハッシュは SHA-1 と MD5 です。PCで `sha256sum` を取っておくと確実です。
- 実機1台(公式 v2.60)で確認: `mtd0` を2回読んで一致し、CH341Aで取った原本ダンプと比べて、**カーネル(KNL)スロット以外は完全に一致**しました
  (そのときのKNLスロットは自作カーネルに替えてあったため。無改造の機体なら全域が一致するはずです)。
- テスト: `scripts/stage1/test_backup_sim.sh`(MTD・マウントを模擬ファイルに差し替えた論理テスト。保存・2回目のスキップ・失敗時の起動継続など12件)。


## バックアップへ戻す(`--mode restore`)

SPIのうち、このプロジェクトが書き換えるのは **KNL(カーネル)スロットだけ**です。バックアップから KNL / BKNL の2スロットだけを書き戻す `.dlm` を作れます
(ブートローダ・ECC・RFS などには触れません。書き込みツール `mtdtool` が許可範囲を固定しています)。公式カーネルに戻したいときや、試したカーネルを元に戻したいときに使います。

```bash
# 1. 復元版を作る(PC側。root不要)。mtdtool は scripts/tools/mtdtool.c をMIPS向けにビルドしたもの(docs/09)
python3 scripts/stage1/make_stage1_dlm.py build --official <HDDのsys1にある00550066.dlm> --out spi_restore.dlm --mode restore --mtdtool <mtdtool>
# 2. 差し替える(手順はバックアップ版と同じ)。sys1 または p3 に /spi_backup/spi_mtd0.bin と SHA1SUMS が置いてあること
```

起動すると、次の順に動きます。ログは `/spi_backup/restore.log` に**追記**されます。

1. `spi_mtd0.bin` のサイズが `/dev/mtd0` と同じか、`SHA1SUMS` が合うかを確認します(合わなければ何も書きません)。
2. KNL(`0x100000`〜)と BKNL(`0x380000`〜)を、バックアップの同じ範囲と比べ、**違うスロットだけ**を `mtdtool flash`(消去→書き込み→読み戻し検証)で書きます。
   バックアップ側のスロットが全部 `0xff` または `0x00` なら書きません。KNL が失敗したら BKNL には進みません(カーネルは A/B 冗長なので、片方が無傷なら起動できます)。
3. 書き換えがあって成功したら、再起動します。再起動後は一致しているので何もせず、公式アプリを起動します。失敗や不要の場合も、そのまま公式アプリを起動します。

実機で確認したこと: 自作カーネルが入った状態に対して、バックアップ(自作カーネル入り)を元に実行 → `erased` / `wrote` / `verify OK` → 再起動 → 次の起動のログは「すでにバックアップと同じ。書かない」。
(逆方向、自作カーネル入りから初期のカーネルへ戻す実行も通りましたが、その実行のログは再起動で消えていました。その後の起動のログは「初期のダンプと同じ」で、状態は一致しています。)
模擬テスト(`scripts/stage1/test_restore_sim.sh`、17項目)で、不一致・両方不一致・書き込み失敗・バックアップ破損・サイズ違い・空スロット・先頭が `0x00` のスロットを確認しています。

注意: カスタムカーネルを使ったDebian直起動のHDDは、公式カーネルに戻すと起動しなくなります(公式のminirootに入ります)。直起動に戻すには、自作カーネル入りのバックアップを元に、この `.dlm` をもう一度走らせます。


## 本体のNVを空にする(`--mode nvreset`、`nasne-nvreset`)

SPIには、`mtd0`(ブートローダ・カーネル・RFS)のほかに、**NV領域(`/dev/mtd1`、jffs2、約3MB)**があります。公式アプリはここに、設定(本体名など)と、HDDとの対応・録画まわりの状態を書きます。
**HDDを入れ替えたとき、古いHDD向けのNVが残っていると、新しいHDDと食い違って、公式アプリが起動の約40秒後に固まります**([docs/04](04_hdd_recovery_guide.md))。NVを空(全部 `0xff`)にすると、公式アプリは固まらずに、NVを作り直します。

- **公式のHDDだけで使う**(Debianを入れていない): `--mode nvreset` の `.dlm` を作って、HDDの sys1 に差し替える(手順は上の `--mode restore` と同じ。`--mtdtool` が要る)。
  起動すると、**先にいまのNVを sys1 の `/spi_backup/nv_before_reset_<番号>.bin` に保存**し(保存できなければ消さない)、NVを空にして(消去→書き込み→読み戻し検証)再起動し、公式アプリを起動します。
  **1回だけ**: `/spi_backup/nv_reset.done` が残り、次の起動からは何もしません(もう一度行うには、このファイルを消す)。実機で確認済み(模擬テスト `test_nvreset_sim.sh` 13項目も)。
  **Debianを入れた機体では使わない**: 「公式を1回だけ起動」(`official-once`)の印を消すブロックを持たないため、Debianに戻れなくなる(sys1 を元の `.dlm` に戻す必要がある)。
- **Debianが動いている**: `nasne-nvreset`(`prepare_tree.sh` が入れる)。`save`(NVを保存)、`reset --yes`(保存してから空にする)、`restore <ファイル>`(書き戻す)。実機で、保存→リセット→書き戻しのmd5一致を確認。

注意: NVを空にすると、**本体の設定(名前など)は初期値に戻ります**。録画の一覧は、HDD側の状態によって見えなくなることがあります(実機で、食い違いで固まった後にNVを空にしたら、録画の件数が0になった)。
保存したNVは、いつでも書き戻せます。保存したNVの中身は、jffs2が(マウントされた時点で)書き換わるため、元のダンプとはバイト単位では一致しません。

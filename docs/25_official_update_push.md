# 25. 公式アップデート経路でカスタム.dlm を適用する(push 方式)

> **層**: 公式ファームのアップデート機能と Web API。

公式ファームウェアには「サーバーからアップデートファイルをダウンロードして適用する」機能があります。
この機能を PC から駆動すると、**HDD を取り出したり SPI を書き換えたりせずに、純正のまま動いている nasne へ
自作の `.dlm` を公式の適用処理で書き込む**ことができます。本書は、その経路の仕組み、前提、ツールの使い方、
投げる用の `.dlm` の作り方、失敗時のエラーコード表をまとめたものです。

確認できている範囲: 公式パッケージと同型の自作 KRST パッケージが、公式の適用段を通って起動するところまでを
複数回確認済みです。失敗する場合の理由 (版ゲート・容量) も特定できています。

## 1. 仕組み

- PC 側から公式 Web API (ポート 64210) の `POST /config/updateFileDownload` を呼び、
本文に `fileURL=<PC 側で HTTP 配信する.dlm の URL>&forcedUpdate=1` を渡します。
本体はその URL へファイルを取りに行き、ダウンロードできたら公式の適用処理 (適用段) で書き込み、再起動します。
- 認証は [docs/17](17_official_web_api.md) の `X-DTVToken` です
(`base64( SHA1( PIN + パス + 本文の先頭256文字))`、PIN は本体 MAC アドレスの下位 3 オクテット)。
MAC は `GET /status/networkIfInfoGet` で誰でも取得でき、秘密ではありません。
- ダウンロード段の検査は **CRC32 のみ** です (この経路に署名検証はありません。
ファーム形式そのものについては [docs/03](03_firmware_format.md))。
- 適用段は sys1 (HDD の第1パーティション) 上で世代交代の形で書き込みます:
現行バンク一式を退避先へコピーしてから、新しいセグメントを所定のファイルへ書き出し、再起動します。
- 進み具合は `GET /config/updateProgressGet` の `status / completePercent / reason` で見ます (読み方は §6)。

## 2. 前提・使う状況

- 純正の公式ファームで動いている nasne が、LAN から到達できること (Web API が応答すること)。
- 配信する PC が、本体から HTTP で到達できること (本体がファイルを取りに来る形です)。
- **版ゲート**: 投げるパッケージの版が**現行より新しくないと、適用されずに却下されます** (エラーコード表の reason 8)。
同じ版も、古い版も対象で、`forcedUpdate=1` を付けても回避できません。つまりダウングレードはできません。
- 版は、パッケージ内の DLM セグメントのヘッダ `+0x08` major と `+0x0A` の値で決まります。
画面や API に出る版表示は `0<major><+0x0A を10進2桁>` です (例: major=2、+0x0A=60 → `0260`)。
- 一度ある版を適用すると、それ以下の版は二度と適用できなくなります (**版の消費**)。
実験用の版番号は、公式に存在しない値を使い、将来分を見越して間隔を空けて付けてください。
- **容量の前提**: 適用段は sys1 に、現行バンク一式の退避コピー (公式構成で約 36 MB) と
新規パッケージ全量の書き込みを行います。**sys1 の空き容量がこのピークに足りないと、
ダウンロードは成功しても適用で失敗します** (reason 4)。パッケージ自体に固定のサイズ上限は
ありません (適用側のコードに上限値は無いことを確認済み) が、ピークの書き込み量が
sys1 の空きを超えないことが必要です。sys1 に大きなファイルを溜めている場合は先に空きを確認してください。
- 適用が通っても、中身が起動するとは限りません。起動に失敗した場合の戻り方は §3 のとおりですが、
万一に備えて SPI の書き戻し手段などを用意してから実験してください。

## 3. フォールバックの挙動

適用後に新しいイメージの起動が滞ると、本体は自律的に前のイメージへ戻ります (A/B フォールバック)。
実測では約 8〜8.5 分で戻りました。戻った後は:

- `softwareVersion` (現行版) = 前の版
- `backdatedVersion` = **失敗した版** (戻された版がここに残ります)

つまり「適用されたか」は再起動後のこの2つの値で見分けます (§5 の最終判定)。
適用前の却下 (reason が付く失敗) では、本体は再起動せず、版も変わりません。

## 4. 投げる用の.dlm の作り方

### 4.1 パッケージの形

公式アップデートで配られるファイル (例: 公式の `KRST3101_0260_SECURE.dlm`) は、
**KNL ‖ RFS ‖ DLM の3セグメントを連結した KRST パッケージ** です。各セグメントは
「64 バイトのヘッダ (独自 Blowfish 変種で暗号化) + ボディ」で、ヘッダの主な項目は次のとおりです。

| オフセット | 内容 |
|---|---|
| `+0x00` (4B) | マジック (`KNL\0` / `RFS\0` / `DLM\0`) |
| `+0x04` (BE32) | セグメント全長 (ヘッダ込みの宣言サイズ) |
| `+0x08` (BE16) | major |
| `+0x0A` (BE16) | 版サブ (版表示の下2桁) |
| `+0x0C` (BE16) | 補助フィールド |
| `+0x0E` (1B) | flag (1 = ボディも暗号化、0 = 平文) |
| `+0x10` (4B) | hwtype |
| `+0x14` (32B) | 日付文字列 |
| `+0x3C` (BE32) | CRC32 (この欄を 0 で埋めたヘッダ 64 バイトに続けてボディを通した CRC32) |

DLM セグメントが rootfs で、KNL / RFS はそのまま公式のものを流用します。
**DLM セグメント単体だけのパッケージが適用できるかは未検証** です (公式の配布物は常に3セグメント連結)。
KRST の形で作ってください。

### 4.2 手順

1. 公式 KRST パッケージを用意します (公式サーバーから取得できる正規の配布物)。
2. 差し替えたい rootfs (tar.gz) をボディにした DLM セグメントを作ります。
- `scripts/stage1/make_stage1_dlm.py build --official <公式KRST> --out seg.dlm` は、
公式 KRST から DLM セグメントを取り出して土台にし、rcS 差し替えなどの段階1用セグメントを作ります。
- rootfs の tar.gz をそのままボディにする場合は `scripts/build_dlm.py build --template <公式DLMセグメント> --body rootfs.tar.gz --out seg.dlm` でも作れます。
- **ボディは flag=0 (平文) で構いません**。適用段は flag=0 の平文ボディを受け付けることを確認済みです。
hwtype と日付文字列は、土台にした公式セグメントの値がそのまま引き継がれます。
3. `scripts/stage1/build_krst_package.py` で、公式の KNL / RFS と連結して KRST パッケージにします。
このとき DLM ヘッダへ次の後加工を行います。
- **宣言サイズ `+0x04` を実長にする**。適用段は宣言サイズで連結を辿るため、
テンプレートの値 (公式セグメントのサイズ) が残っていると連結が破綻します。必ず実長に直してください。
- `+0x08` major と `+0x0A` に、狙う版を設定する (現行より新しい版。§2 の版ゲート)。
- CRC32 を再計算する。

```bash
# セグメント (stage1 の例) を作って、版 3.61 の KRST パッケージにまとめる
python3 scripts/stage1/make_stage1_dlm.py build --official KRST3101_0260_SECURE.dlm --out seg.dlm --mode p3
python3 scripts/stage1/build_krst_package.py --official KRST3101_0260_SECURE.dlm \
--segment seg.dlm --major 3 --sub 61 --out custom_krst.dlm

# rootfs の tar.gz から直接まとめる場合
python3 scripts/stage1/build_krst_package.py --official KRST3101_0260_SECURE.dlm \
--body rootfs.tar.gz --major 3 --sub 61 --out custom_krst.dlm
```

4. 投げる前に `scripts/push/nasne_push.py inspect custom_krst.dlm` で検査します
(セグメント構成・宣言サイズと実長の一致・CRC・版表示)。

## 5. push ツールの使い方

`scripts/push/nasne_push.py` (Python 標準ライブラリのみ。ヘッダ復号に `scripts/dlm_crypto.py` を使います)。

```bash
# 検査だけ (機体には触れない)
python3 scripts/push/nasne_push.py inspect custom_krst.dlm

# 計画確認 (検査 + 機体の現行版との比較。送信はしない)
python3 scripts/push/nasne_push.py push custom_krst.dlm --host <nasneのIP>

# 実際に投げる
python3 scripts/push/nasne_push.py push custom_krst.dlm --host <nasneのIP> --yes
```

安全弁と判定のしかた:

- `--yes` を明示しない限り送信しません (ドライランとして計画表示で終わります)。
- CRC 不一致・サイズ不整合のファイルは送信しません (終了コード 2)。
- 版ゲートに確実に引っかかる場合 (対象の版が現行以下) は、送信前に止まります (終了コード 3)。
- 送信後は `updateProgressGet` を監視しますが、**成否の最終判定は進捗 API だけで行いません** (§6 の注意)。
再起動後の `softwareVersionGet` で、`softwareVersion` が目標の版に一致し、かつ
`backdatedVersion` が目標の版と異なることを成功の条件とします。
`backdatedVersion` が目標の版なら、適用はされたが起動に失敗してフォールバックした、という判定です。

終了コード:

| コード | 意味 |
|---|---|
| 0 | 成功 (現行版が対象版になったことを確認)。ドライラン完了も 0 |
| 1 | 一般エラー (機体への問い合わせ失敗、送信失敗、errorcode!= 0 など) |
| 2 | ファイル検査 NG (CRC 不一致・サイズ不整合) |
| 3 | 版ゲートの事前チェックで停止 (対象が現行より新しくない) |
| 4 | 機体に却下された (進捗が reason!= 0 で終了) |
| 5 | フォールバックした (適用後の起動失敗で前版へ戻った) |
| 6 | 判定不能 (期限内に終了・版確認が取れなかった) |

オフラインのテストが `scripts/push/test_nasne_push.py` にあります (合成したパッケージと
モックの Web API を使うため、実機も実ファイルも不要です)。

## 6. 進捗 API の読み方と reason (エラーコード表)

`GET /config/updateProgressGet` が返す `status / completePercent / reason` の読み方です
(パスは `/config/` です。`/status/updateProgressGet` は 404 になります)。

- `status`: 2 = 処理中、0 = 正常終了、1 = 待機中または失敗して終了。
- `completePercent`: 主にダウンロードの進み具合です。適用はその後に短時間で進みます。
- `reason`: 終了理由。下の表のとおりです。処理中は 0 です。
- **値は処理が終わっても残り、次の試行まで残留します**。送信前の値を控えておき、
「送信前から変化したか」を併せて見ないと、前回の失敗を今回の結果と取り違えます。
- 再起動の間は API 自体が応答しなくなります (異常ではありません)。
また再起動直後は `softwareVersionGet` が一時的に `errorcode 303` を返すことがあります。

### reason 表

| reason | 意味 | 根拠 |
|---|---|---|
| 0 | 正常 (処理中、または正常終了) | 実測 |
| 1 | 適用段の失敗: ヘッダ検査 (areaheadCheck) の失敗 | 静的解析 |
| 2 | 適用段の失敗: データ部の CRC32 不一致 | 静的解析 |
| 3 | 適用段の失敗: ファイル終端処理の異常 (詳細な発生条件は未確定) | 静的解析 |
| 4 | 適用段の失敗: sys1 への書き出しの失敗。主因は空き容量不足 (退避コピー + 新規書き込みのピークが空きを超えた) | 実測 + 静的解析 |
| 5 | ダウンロード段の失敗: ネットワークエラー (`bad address` / `No route to host` / `Connection timed out`) | 静的解析 |
| 6 | ダウンロード段の失敗: 本体の状態変化による中断 | 静的解析 |
| 7 | ダウンロード段の失敗: 所要時間の超過で取得を打ち切った | 静的解析 |
| 8 | 版ゲート (現行より新しくない) を含む「その他」。適用段・ダウンロード段のその他の失敗 (取得先の 404 など) もここに合流する | 実測 + 静的解析 |
| 9 | 失敗ではありません。待機状態の値です (待機時は `status 1 / completePercent 0 / reason 9`) | 実測 |

仕組み (静的解析で確定): 本体は適用段とダウンロード段で別々の内部結果コードを持ち、
それを変換して reason にしています。適用段は内部 `-2 → 1`、`-3 → 2`、`-4 → 3`、`-5 → 4`、
それ以外 (版数チェックの失敗を含む) `→ 8`。ダウンロード段は内部 `-3 → 5`、`-4 → 6`、`-5 → 7`、
それ以外 `→ 8` です。reason 4 の内部結果 `-5` には、書き出しの失敗のほかに
「未知のマジック」「読み取り長の不一致」などの合流経路もありますが (実測では未確認)、
実際に起きた事例では sys1 の容量不足が原因でした。

## 7. 注意

- 投げるたびに版フロアが上がります。版番号は使い捨てのつもりで付けないでください。
- reason 8 だけでは版ゲートかどうかを断定できません (他の失敗も合流します)。
版の新旧関係と、ダウンロードが済んだか (進み具合) を併せて判断してください。
- 却下された場合は反射的に次の版を投げず、まず reason と sys1 の空き、版の関係を確認してください。
- 本書の方法は公式の適用処理を使うため、適用段の検証 (CRC・版・容量) はすべて公式側の判定に従います。
HDD へ直接ファイルを配置する方法 (例: [docs/16](16_spi_backup_dlm.md)) とは前提が異なる点に注意してください。

# 06. 約333秒ごとのリセット(MCUウォッチドッグ)と、止め方

## 結論

Sony のユーザランド抜きで起動すると、**約333秒(約5.5分)ごとに本体がリセットされる**。原因は SoC の外にある**MCU(基板上のマイコン)のウォッチドッグ**で、
純正の `procmng` は起動直後にこれを止めている。止め方:

> 公式ドライバ(`xcode4drv`)のI2C ioctl で、**MCU(I2Cバス0、8bitアドレス `0x20`)へ `[0x20, 0x01]` を1回書く**
> (`procmng` の文字列 "MCU Watchdog Disable" と同じ操作)

SoC内のWDTレジスタ(`WDT_TIMER0` など)を最大値にしても止まらない(MCU側のため)。Linux標準のwatchdogデバイスも無い。

検証: 手動で書いた場合は1000秒超、起動時サービス化したあとも連続稼働して、リセットは起きなかった(書かないと333秒で落ちる)。

## 使い方(Debian側)

前提: 公式ドライバ `xcode4drv.ko` と `rc.xcode4` が `/usr/local/sbin/` にあること(公式ファームのrootfsの `/opt/dtvtuner/lib/modules/` にある。
`ofw_tool.py` と `dlm_crypto.py` でrootfsを取り出す。SIEのGPLソース `AVDriver7GSP47.zip` にも同世代のものが入っているが、こちらは未検証)。

```bash
# MIPS用にビルド(Dockerの nasne-kcc:gcc432 環境。docs/05)
mipsel-linux-gcc -nostdlib -static -fno-pic -mno-abicalls -mips32r2 -O2 -e __start -o mcui2c scripts/watchdog/mcui2c.c
scp mcui2c root@<nasne>:/usr/local/sbin/
scp scripts/watchdog/nasne-mcu-wd root@<nasne>:/etc/init.d/
ssh root@<nasne> 'chmod +x /etc/init.d/nasne-mcu-wd; update-rc.d nasne-mcu-wd defaults 05'
```

`nasne-mcu-wd` は起動のたびにドライバを読み込み(`rc.xcode4`)、`mcui2c w 20 20 01` を成功するまで繰り返す。ログ: `/var/log/nasne-mcu-wd.log`。

単発で試すだけなら:

```bash
cd /usr/local/sbin && ./rc.xcode4 && ./mcui2c w 20 20 01       # "mcui2c write addr8=20 n=02 ... (COMPLETE)"
./mcui2c r 20 6                                                 # MCUのステータス6バイトを読む
```

## MCUのコマンド(`procmng` の逆コンパイルから)

MCU(I2Cバス0、8bitアドレス `0x20`)への書き込みは `[レジスタ, 値]` の2バイト。

| 書き込み | 使われる場面 |
|---|---|
| `[0x20, 0x00]` | メインループが**約5秒ごと**に送る(心拍) |
| `[0x20, 0x01]` | **MCU Watchdog Disable**。シャットダウン処理(`/sbin/halt` の前)と、init失敗時 |
| `[0x01, 0x00 / 0x2f]` | 起動完了時 |
| `[0x08, 0x00]` `[0x40, 0 / 3 / 5]` | 起動シーケンス中 |
| `[0x04, 0x02]` | リブート関連(引数ありのとき)。意味は未検証 |
| `[0x10, 0x2a / 0x32 / 0x51]` | 0x51 = シャットダウン時、0x32 = initの電源断前、0x2a = エラー点滅ループ。レジスタ0x10は動作モード/表示コード類(未解析) |
| `[0x02, …]` `[0x04, 0x01]` | 電源・タイマ関連(未解析) |

MCUの読み出しは6バイト(各バイトの意味は未解明。最終バイトはカウンタのように増える)。

## I2Cドライバ側の手順(ソースより)

`drv/i2c.c` の `i2c_submit_command` は、SoC内蔵のハードウェアI2Cブロック `i`(0/1)を次の手順で使う。
①HWミューテックス `MIPS_INTERLOCK1` のID4にドライバID(9)を書いて取得、②`GPIO_I_CTRL` のビット `(29-i)` を落としてI2Cマスタモードにする、
③データを `DATA_LOAD`、`CONFIG`(atomic_period / timeout)、`COMMAND`(slave<<16 | rop<<12 | start<<8 | stop<<9 | bytes)に書いて起動、
④`PPC_INT_STATUS` の XFERDONE / ARB_FAIL / BUSY_ERROR で完了判定。スレーブアドレスは**8bit表記を `>>1`** してコマンドに入れる。
公式のバス速度は既定 **10kHz**(`atomic_period = 6750000 / 周波数`、`timeout = 500×27/4`)。

> ⚠️ **`/dev/mem` でSoCのI2Cレジスタを直接叩いてはいけない。** 公式ドライバと同じ手順を再現しても、ブロック0はNACK/ARB_FAILになり、
> **MCU側のI2Cが固まって、ドライバ経由の通信も失敗し続け、SoCのリセットでも直らず電源サイクルが必要になった**。
> I2Cは必ず公式ドライバのioctl経由(`mcui2c` / `i2cx`)で行うこと。HWミューテックスの絡みがあると考えられる。

## 電源オフ・予約起動・電源ボタン

**公式は、電源ボタンの長押しで電源オフにできます**(待機約0.7〜1W、全LED消灯。実機で確認)。Debianでも、次のとおり**電源オフと予約起動ができます**。

### 電源を切るMCUコマンド(実機で確認)

| コマンド | 意味 |
|---|---|
| **`[0x02,0x01]`** | **電源断**。MCUが基板の電源を切る(待機約1W)。公式 `procmng` が終了処理の最後に送るコマンド |
| **`[0x02,0x02,b3,b2,b1,b0]`** | **起床タイマ**(32ビット、上位バイトから)。電源を切ってからこの時間後に、MCUが自動で電源を入れる。**1カウント≒10.5ms(毎秒約95カウント)**。電源が入ってからpingが通るまでに約30秒かかる |
| `[0x10,0x51]` | 表示コード「終了」(LEDが消える)。これだけでは電源は切れない |
| `[0x04,0x02]` | 再起動要求(カーネルの再起動処理がMCUへ送る) |
| `[0x04,0x01]` `[0x40,x]` `[0x20,0x01]` | **単独では電源が切れない**(試験済み)。電源断の合図は `[0x02,0x01]` だった |

起床タイマの実測(設定値 → 電源が切れてからpingが戻るまで): 3000 → 62秒、6000 → 98秒、12000 → 156秒、30000 → 345秒、
およびサービス経由で120秒 → 152秒(傾き≒10.5ms/カウント、切れてからの固定の遅れ≒30秒)。**最大は32ビット(約50日)**。
起床で起動した場合、MCUステータス2バイト目のbit1(`0x02`)が立つ(`13 80 ..` → `13 82 ..`)。タイマ起床の判別に使える。

**`[0x02,0x02,…]` は、書いた時点(約1.5秒後)に電源が切れる**(実機で確認。`[0x02,0x01]` を送らなくても切れる。書き込みの ioctl は戻らない)。
つまり「起床タイマを設定して電源を切る」コマンドで、電源断の直前の準備(HDD のスタンバイ、表示コード `0x51`)は、**タイマを書く前**に済ませる。
実測(タイマだけを書いた場合): 1000 カウント → 切れてから pingが戻るまで 43.6秒、5000 → 82秒(2回とも)、**いずれも設定どおり**(カウント÷95 + 約33秒の起動)。
起床時刻の精度は良く、設定した時刻の約30秒後(起動の時間)に ping が通る。以前、5000 カウントで約10秒で戻ったように見えた件は、再現しなかった(上の値のとおり正常)。
起床で起動した場合のステータス2バイト目の bit1(`0x02`)は、次に電源を切るまで立ったまま(起動の約40秒後も `13 82`)。

電源を切ったあとは、電源ケーブルを15秒以上抜き差ししても起動し(ボタン不要)、電源ボタンでも起動する。

### Debianでの電源オフ(`scripts/watchdog/a-nasne-poweroff`)
カーネルの `halt` / `poweroff` は `wait` ループで止まるだけで、MCUへ何も送らないため、そのままでは電源が切れません(約6Wのまま)。
そこで、`rc0.d` のシャットダウン処理の最後(ルートが読み取り専用になった `umountroot` のあと、`halt` の前)に、HDDをスタンバイにして
`[0x10,0x51]` → `[0x02,0x01]` を送る init スクリプトを入れました(`poweroff` / `halt` で実行、`reboot` には影響しません)。
`/etc/default/nasne-poweroff` の `WAKE_SECONDS=<秒>` を書くと、その秒数後に自動で起動します(0 または未設定ならタイマなし)。
`poweroff` コマンドだけで電源が切れ、再起動後のファイルシステムは `clean`(復旧なし)であることを確認しました。

### 録画予約に合わせて起こす(`nasne-waked`、EPGStation 連動)
電源を切った nasne を、EPGStation の予約の少し前に自動で起こします(公式が予約録画のためにやっているのと同じ)。

- `nasne-waked`(Perl の常駐)が、EPGStation の予約(`GET /api/reserves`。読むだけ)を定期的に読んで、**次の予約の開始 − 余裕(既定300秒)**を「起こす時刻」として `/var/lib/nasne-wake/next` に書く。開始済みの予約は除く。近すぎるときは60秒後。
- `poweroff` のとき `a-nasne-poweroff` がそのファイルを読み、(起こす時刻 − いま)秒後にタイマをセットして電源を切る。`/etc/default/nasne-poweroff` の `WAKE_SECONDS` も書いてあれば、**短いほう**にする(予約が無い・あとから追加されたときのために、たまに起きる、という使い方ができる)。最大は40日。
- なぜ常駐か: `poweroff` の最後はネットワークが落ちたあとで、EPGStation に聞けない。動いているうちに聞いて、書いておく。
- **時計**: nasne には RTC が無く、起動直後の時計は前回の停止時刻で、NTP(`ntpdate`)で数十秒後に直る。そこで、EPGStation の応答の `Date` ヘッダとの差を使い、「nasne の時計で何時に起こすか」を書く。起動後10分は60秒ごとに聞き直す。
- 設定: `/etc/default/nasne-wake`(**`NASNE_WAKE_URL=http://<EPGStationのホスト>:8888` が必須**。無ければ何もしない)、`NASNE_WAKE_LEAD`(予約の何秒前に起こすか。既定300。起動に約35秒、Mirakurun がチューナーを使えるまでの余裕)、`NASNE_WAKE_POLL`(既定300)、`NASNE_WAKE_ENABLE=0` で無効。`/etc/init.d/nasne-wake restart` で反映。`perl /usr/local/sbin/nasne-waked --once` で、次の予約と起こす時刻だけ確認できる。
- 電源を切るのは、既定では**手動**(電源ボタンの長押し、`poweroff`)。EPGStation に予約を**追加したとき**は、次に `nasne-waked` が聞くまで(既定300秒)は反映されない。電源が切れている間に追加した予約は、次に起きるまで反映されない。
- **自動電源オフ(任意。`NASNE_WAKE_AUTOOFF=1`)**: 公式がやるのと同じく、タイマ起床したあと、使われなくなったら自分で `poweroff` する。次の**すべて**を満たしたときだけ切る(手動で電源を入れた・ssh で使っている・視聴/録画中・予約が近い、のどれかなら切らない):
  1. **タイマ起床で起動した**(MCUステータス2バイト目の bit1。手動の電源投入では立たない)
  2. 起動から5分以上
  3. チューナーが使われていない(`nasne-recpt1` のロック。番組表の取得も含む)
  4. ssh のセッションが無い
  5. 3・4 の状態が `NASNE_WAKE_IDLE` 秒(既定600)続いた
  6. EPGStation の予約が最近確認できていて、**次の起床まで `NASNE_WAKE_MIN_OFF` 秒(既定600)以上**ある(予約が無ければ、それも可)
  切る直前にもう一度 EPGStation に聞いて確かめる。EPGStation に繋がらないときは**切らない**(予約を確認できないため)。判定は uptime で測る(NTP の時刻補正で狂わない)。`perl /usr/local/sbin/nasne-waked --once`(`NASNE_WAKE_AUTOOFF=1` を付けて)で、判定だけ確認できる(実行はしない)。
  ホスト上の試験(疑似の EPGStation・MCU・poweroff)で、タイマ起床+アイドル+予約が遠い → 切る、手動起動 / ssh 接続あり / 予約が近い / チューナー使用中 → 切らない、予約なし → 切る、を確認した。
- **実機で確認済み**: 約15分後の予約(2分間)を作る → `nasne-waked` が起こす時刻を書く → `poweroff` → 起こす時刻の約30秒後に ping が戻る → 予約の時刻に録画が始まり、2分間のTS(約230MB)が保存された。
- すでにイメージに入っている Debian には、dlm を差し替えても入りません。`nasne-waked` `nasne-wake`(init)`a-nasne-poweroff` を置き、`update-rc.d nasne-wake defaults 27`。

### 電源ボタンの長押し(`scripts/watchdog/nasne-powerbtn`)
長押しは、MCUのステータス(`mcui2c r 20 6` の6バイト)の**2バイト目のbit4(`0x10`)がラッチ**されます(`13 80 ..` → `13 90 ..`)。短い押下ではラッチされません。
公式 `procmng` がこのビットを見て終了処理に入ります(2バイト目のbit7はウォッチドッグ停止中、bit1はタイマ起床、bit0・2・3・5も起動要因とみられます)。
`nasne-powerbtn` は、このビットを1秒ごとに読み、「立っていない→立った」の変化で `poweroff` する常駐プログラムです(起動時にすでに立っていた分は無視)。
**実機で確認済み**: 電源ボタンを長押しすると、検出から数秒で `poweroff` が走り、電源が切れます(再起動後のファイルシステムは `clean`)。
ラッチは、電源を切って入れ直す(コールドブート)とクリアされます(`13 90 ..` → `13 80 ..`)。**ソフトウェアの再起動(`reboot`)ではクリアされません**(実機で確認: ラッチが立ったまま `reboot` すると、約3.5分後も `13 90`)。クリアするコマンドは見つかっていません。
そのため、ラッチが残ったまま `reboot` すると、次の長押しは(bit が立ったままなので)電源を入れ直すまで検出できません。通常は「長押し → `poweroff` → コールドブート」なので問題になりませんが、`nasne-powerbtn` は次のように作ってあります:
- 起動直後は MCU のドライバがまだ無いことがあるので、**最初の読み取りが成功するまで待つ**(失敗を「ラッチなし」と見なすと、残っているラッチを新しい長押しと取り違えて `poweroff` する)。
- `reboot` で止めるとき(rc6 の stop)に、そのときのラッチの値を `/var/lib/nasne-powerbtn.reboot` に残す。起動時に、ラッチが立っていて**かつ**そこにも立っていたなら「`reboot` をまたいだ古いラッチ」として無視し、そうでなければ「起動中に押された長押し」として `poweroff` する(コールドブート後のラッチは必ずクリアされているので、立っていれば押されたということ)。
実機で、ラッチが残ったままの `reboot` → 起動後に無視されて稼働を続ける、コールドブート後は通常どおり(`reboot前=-1`)を確認した。

### 公式の終了処理の順序(観測と静的解析)
表示コード `[0x10,0x29]` → サービス停止(`smbd`/`nmbd`)→ `udhcpc` 停止(ネットワーク断)→ 全プロセスへ `SIGTERM`/`SIGKILL` → `sync` ×2 →
`echo 60000 > /proc/sys/vm/dirty_writeback_centisecs` → 起床タイマの計算と設定(次の録画予約までの秒数×1000÷12のカウント、無ければ300000カウント)→ アンマウント →
`[0x02,0x01]` → 無限ループ。公式は、予約録画のためにタイマ起床を使っているとみられます。

## LED

### PWR LED: MCUの「表示コード」レジスタ(0x10)で点灯できる ✅

PWR LED(緑)は **MCUが駆動**している。電源投入後は1Hzで点滅し、**MCUのレジスタ `0x10`(表示コード)に `0x32` を書くと点灯に変わる**(公式 `procmng` が通常運転中に書く値)。

```bash
mcui2c w 20 10 32      # PWR LED 点灯(点滅 → 点灯)。ウォッチドッグを止めた状態でも、止めていない状態でも効く
```

`nasne-mcu-wd`(起動時サービス)が、ウォッチドッグを止めたあとにこれを書くので、Debian起動の約1分後(サービスが走ったとき)にPWRが点灯する。
Webカメラでnasneを撮って確認した(点灯は30秒以上保持、再起動後も同様)。

表示コード(`[0x10, 値]`)を値ごとに書いて、PWR LEDの様子をカメラで観測した結果:

| 値 | PWRの様子 | 公式での用途 |
|---|---|---|
| `0x32` | **点灯**(固定) | 通常運転(HDDが正常なとき) |
| `0x00` | 消灯 | 一部の状態 |
| `0x26` | 速い点滅(約4Hz) | HDDが異常/未接続の状態で `0x32` の代わりに選ばれる |
| `0x29` / `0x2a` | 遅い不規則な点滅 | エラー表示(`0x2a` は init失敗の点滅ループ) |
| `0x01`〜`0x0f` | 値ごとに違う点滅パターン(`0x04` `0x08` `0x0c` `0x10` は消灯)。下位2bitがパターン、上位がテンポのように見える | (未使用とみられる) |
| **`0x14`〜`0x4f`**(下の「PWR の色」) | **下位2bitで色が決まる**(`00`=消灯、`01`=**赤**、`10`=**緑**、`11`=**橙**)。例: `0x31`=赤の点灯、`0x32`=緑の点灯、`0x33`=橙の点灯。上位のビットは点灯・点滅とテンポ | `0x32`(緑の点灯)が通常運転。赤(`0x31` など)は、公式の `LEDControl` の `powerRed` に当たるとみられる |
| `0x11`〜`0x13` | 点灯 | (未使用とみられる) |
| `0x51` | (書かない)シャットダウン時に `/sbin/halt` の前に書かれる。電源断のコマンドと推定 | シャットダウン |

公式 `procmng` の状態機械(`FUN_0040344c`)は、状態番号から表示コード(`0x2a` / `0x32` / `0x51` / `0` / `0x29`)を表で引いて `[0x10, コード]` を書く。
通常運転(状態2)は `0x32`、HDDの状態を問い合わせた結果が異常なら `0x26`。

MCUに書くコマンドの全体(`procmng` を逆アセンブルして洗い出した12個。すべてバス0・アドレス `0x20` への2バイト書き込み):

| コマンド | 意味(推定を含む) |
|---|---|
| `[0x20, 0x00]` | 心拍(約5秒ごと)。`0x20,0x01` でウォッチドッグ停止 |
| `[0x08, 0x00]` `[0x01, 0x2f]` `[0x40, 0x05]` | 起動完了の通知(順に)。**これだけではPWRは点灯しない** |
| `[0x10, 値]` | 表示コード(上表) |
| `[0x40, 0 / 3 / 5]` | 状態(5=起動完了、3=終了処理、0=電源断経路) |
| `[0x02, 1]` `[0x02, 2, 32bit]` `[0x04, 1 / 2]` | 電源・タイマ・リブート関連(未解析。`[0x04,2]` は procmng のリブート処理) |

MCUのステータス読み出し(6バイト)の末尾2バイトは、**最後にホストからコマンドを受けてからの経過時間(10ms単位のカウンタ)**で、書き込みのたびに0に戻る。
2バイト目の `0x80` はウォッチドッグ停止中のフラグ(停止すると `13 80 …`、有効だと `13 00 …`)。

### PWR LED は3色(赤・緑・橙)。色は表示コードの下位2bitで決まる ✅

`0x14`〜`0x4f`(`0x50`〜`0x5f` はシャットダウン系の可能性があるので試していない)の表示コードを順に書いて、Webカメラで色と点滅を調べた(実機1台)。

| 下位2bit | 色 | 例 |
|---|---|---|
| `00` | 消灯 | `0x14` `0x18` `0x1c` `0x20` `0x24` `0x28` `0x2c` `0x30` `0x34` `0x38` `0x3c` `0x40` `0x44` `0x48` `0x4c` |
| `01` | **赤** | 点灯: `0x15` `0x19` `0x1d` `0x2d` `0x31` `0x35` `0x39` `0x3d` `0x41` `0x4d` / 点滅: `0x21` `0x25` `0x45` `0x49` |
| `10` | **緑** | 点灯: `0x16` `0x1a` `0x1e` `0x22` `0x2e` `0x32`(通常運転)`0x36` `0x3a` `0x3e` `0x4e` / 点滅: `0x26` `0x46` `0x4a` |
| `11` | **橙**(赤+緑) | 点灯: `0x17` `0x1b` `0x1f` `0x23` `0x2f` `0x33` `0x37` `0x3b` `0x3f` `0x43` `0x4f` / 点滅: `0x27` `0x2b` `0x47` `0x4b` |

- 上位のビット(`code >> 2`)が、点灯・点滅と点滅のテンポを決めているとみられる(例: `0x2d`・`0x31`・`0x35`・`0x39`・`0x3d` は、いずれも赤の点灯)。
- 公式の `LEDControl` API の `powerGreen` / `powerRed` は、PWR の緑・赤にあたる(実機で確認。緑と赤の両方で橙)。`LEDControl` は約1秒の一時的な上書きで、過ぎると公式の通常表示に戻る。公式の「PWR/REC 赤点灯」(NV と HDD の食い違いで固まったとき)は、公式アプリが赤の状態コードを書いた結果と推測される(対応する表示コードは、静的解析で未確定)。
- 点滅するコードは、撮影の瞬間によって、明暗や色の判定が揺れる(`0x42` など)。色は、点灯するコードで確認した。
- スキャン用のスクリプト: 開発版の `scripts/camera/pwr_color_scan.py`。

### 前面の4つのLED(PWR / REC / LAN / HDD)の駆動 ✅

前面のLEDは4つ。PWR(緑)が上で、REC・LAN・HDD は離れて並ぶ。Webカメラで、1つずつ点灯・消灯して対応を確認した(実機1台):

| LED | 色 | 駆動 | 操作 |
|---|---|---|---|
| **PWR** | **緑・赤・橙の3色** | **MCU**(I2Cの表示コード。色は下位2bit。上の表) | `mcui2c w 20 10 32`(緑の点灯)、`31`(赤の点灯)、`33`(橙の点灯)など |
| **REC** | **赤** | **SoCのGPIO「ポート10」のビット `0x100`**(High で点灯) | `physio w 1ffffc64 <値>` |
| **LAN** | **橙** | **SoCのGPIO「ポート10」のビット `0x200`**(High で点灯) | 同上 |
| **HDD** | **橙(〜黄)** | **ディスクのアクセスに連動**(ソフトのGPIOではない。SATAコントローラ(AHCI)のアクティビティLED機能とみられる。起動ログに `led` のフラグ) | 操作不要(ディスクを読むと点く) |

- GPIO ポート10 の出力レジスタは物理 `0x1FFFFC64`(`0xBFFFFC64`)、出力許可は `0x1FFFFC68`。Debian の起動後の値は OUT=`0x4e`、EN=`0x34e`(`0x100`・`0x200` は出力許可済み、消灯)。**他のビットはリセットや電源などにつながっている可能性があるので、書くのは `0x100` と `0x200` だけ**にして、読んだ値の他のビットは変えない。
- REC と LAN の割り当ては、LEDの並び(左から PWR・REC・LAN・HDD)と色(赤・橙)からの判断。公式のAPI(`/config/LEDControl`)の `record` / `network` でも、REC / LAN に当たることを確認した。
- GPIOポートNのレジスタは `0xFC04 + 0x10×(N-4)`(`init` / `procmng` のコードより)。

#### Debian での点灯(`nasne-ledd`、既定で組み込み)

REC・LAN は公式と同じ動き、PWR は Debian 独自の「異常表示」:

- **REC(赤)**: **チューナー使用中**(録画・視聴・番組表の取得を含む)に点灯、それ以外は消灯。判定は、`nasne-recpt1` がセッション中だけ持つ排他ロック(`/tmp/nasne-recpt1.lock`)が `/proc/locks` にあるかどうか(**読むだけで、チューナーのロックには干渉しない**。`nasne-recpt1` は変更していない)。
- **LAN(橙)**: 起動中は消灯。**デフォルトルートができたら点灯し、以後ずっと点灯**(点滅しない)。
- **PWR**: 通常は緑(`nasne-mcu-wd` が点灯させる)。**状態ページ(`nasne-statusd`)が異常(`warnings` あり)を報告している間だけ、赤の点灯(表示コード `0x31`)**にし、異常が消えたら緑(`0x32`)に戻す。`nasne-ledd` が `127.0.0.1:8302/status.json` を30秒ごとに見て、2回続けて同じ結果になったら切り替える(ばたつき防止)。状態ページに繋がらないとき(無効・起動前)は PWR に触らない。無効にするなら `NASNE_LED_PWR_WARN=0`、間隔は `NASNE_LED_WARN_POLL`(秒)。実機で、異常→赤、正常→緑の切り替えをカメラで確認した。
- 仕組み: `nasne-ledctl`(`rec|lan on|off`、`status`。libc 不使用の小さな静的バイナリ。GPIO ポート10 の bit `0x100`・`0x200` だけを読んで・変えて・書き、他のビットは保持。`flock` で排他)と、`nasne-ledd`(Perl の常駐。0.5秒ごとに判定し、**変わったときだけ** `nasne-ledctl` を呼ぶ)。`/etc/init.d/nasne-led`(`update-rc.d` で登録)。
- 無効にするなら `/etc/default/nasne-led` に `NASNE_LED_ENABLE=0`、判定の間隔は `NASNE_LED_POLL`(秒)。
- **すでにイメージに入っている Debian には、dlm を差し替えるだけでは入らない**(イメージは再展開されない)。`nasne-ledctl` `nasne-ledd` `nasne-led`(init)を `/usr/local/sbin/` と `/etc/init.d/` に置き、`update-rc.d nasne-led defaults 26`。
- 実機で、受信中の REC の点灯と、受信後の消灯、LAN の点灯をカメラで確認した。Debian の最小構成の Perl には `Time::HiRes` が入っていないので、秒未満の待ちは `select` を使っている。

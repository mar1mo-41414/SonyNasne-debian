# 10. できること・できないこと・未解明

## できること(実機で確認済み)

| 項目 | 内容 | 詳細 |
|---|---|---|
| Debian直起動 | 自前カーネル + 内蔵initramfs で、p3 の Debian wheezy (mipsel) を `sysvinit` PID 1 として起動。ssh / cron / dhcp など通常運用 | [docs/05](05_kernel_and_direct_boot.md) |
| カーネル差し替え | SPIの KNL 領域だけを書き換え。U-Boot / 4段目ブートは無改変(A/B の B を純正のまま残して安全網にする) | [docs/05](05_kernel_and_direct_boot.md) |
| 自前カーネルのビルド | SIE公開のGPLソース + Docker(GCC 4.3.2)でビルド。純正ドライバ `xcode4drv.ko` もそのままロードできる | [docs/05](05_kernel_and_direct_boot.md) |
| 公式ファームの起動 | 自前カーネル上で、公式 v1.00 / v2.60 のユーザランドが起動し、WebUIまで表示される | [docs/03](03_firmware_format.md) |
| 起動失敗時の自動復帰 | 起動カウンタ(2回連続で成功印なし)または `/etc/nasne-direct-boot` の欠如で、純正の起動経路に戻る | [docs/05](05_kernel_and_direct_boot.md) |
| HDDの紐付けの生成 | `00110022.dlm`(個体IDのマネージャ)をオフラインで生成。HDD全損機の復旧、他の本体への移植 | [docs/03](03_firmware_format.md)、[docs/04](04_hdd_recovery_guide.md) |
| ウォッチドッグ停止 | MCUへ I2C で `[0x20, 0x01]`。起動時サービスで自動化 | [docs/06](06_mcu_watchdog.md) |
| **PWR LEDの点灯** | MCUの表示コード(レジスタ `0x10`)へ `0x32` を書く(点滅 → 点灯)。起動時サービスで自動化。Webカメラで確認 | [docs/06](06_mcu_watchdog.md) |
| ブートチェーンの解読 | U-Boot 1.1.3 / 4段目ブート / `.dlm` 暗号 / SPIの地図。署名検証なし | [docs/02](02_boot_chain.md)、[docs/03](03_firmware_format.md) |
| チューナーの選局 | 地デジ(UHF 13〜62)を復調IC/RFチューナーICのI2C操作で選局し、ロック・C/Nを読む | [docs/08](08_tuner_i2c.md) |
| **地デジの受信・復号・配信** | **B-CASカードで復号した元画質(MPEG-2 HD)のTS**を、`recpt1`互換コマンドとHTTPで取り出す。SI(番組表の元データ)も混ぜる。連続2分(約230MB)で同期エラー・スクランブル残りなし | [docs/11](11_tv_streaming.md)、[docs/12](12_ts_and_bcas_decrypt.md) |
| **v1.00なしでのHDD復旧** | 空のHDDから公式 v2.60 だけで起動。HDD登録情報 `.hai` の生成と、p3の初期構造(`p3init`)で、v1.00 を使わずに済む | [docs/04](04_hdd_recovery_guide.md)、[docs/15](15_p3_structure_and_hai.md) |
| **SPIフラッシュの読み出しバックアップ** | 書き込まず、HDDの `00550066.dlm` 差し替えだけで、nasne自身がSPIを読んでHDDに置く(原本ダンプとKNLスロット以外一致) | [docs/16](16_spi_backup_dlm.md) |
| **電源オフ・予約起動(タイマ起床)** | Debianの `poweroff` で実際に電源が切れる(MCUへ `[0x02,0x01]`、待機約1W)。`WAKE_SECONDS` で、切ってから指定秒数後に自動起動(起床タイマ `[0x02,0x02,u32]`、約10.5ms/カウント)。電源ケーブルの抜き差しでも起動 | [docs/06](06_mcu_watchdog.md) |
| **電源ボタン長押しでの電源オフ** | MCUのステータス2バイト目のbit4(`0x10`)がラッチされる(押下で `0x80`→`0x90`)ので、`nasne-powerbtn` が検出して `poweroff` する。実機で「長押し→数秒で電源オフ」を確認 | [docs/06](06_mcu_watchdog.md) |
| B-CASの検出・活性化 | ドライバ経由で、カードの挿入検出と活性化(復号にはカードIDの取得は不要) | [docs/07](07_driver_ioctl_bcas.md) |

## できないこと

| 項目 | 理由 |
|---|---|
| 一部の録画ソフトとの連携 | Mirakurunは動作確認済み(スキャン・番組表・ストリーム)。tvheadend・EPGStation 本体は未検証 |
| 同時に複数の番組・チャンネル | チューナーは1系統・1サービスずつ。2つ目のチューナーの有無や使い方は未調査 |
| BS/CSの受信 | 純正コードの手順を再現した。IF帯を掃引(`nasne_fe.py s-sweep`)したが、試験した入力にはBS/CSの信号が来ておらず(AGCが最大)、**動作は未確認**。BSが来ている入力での試験が必要([docs/08](08_tuner_i2c.md)) |
| B-CASカードIDの取得 | `CARD_ID_ACQUIRE` / `BCASMSG` の応答が返らない(復号には不要) |
| RTC(ハードウェア時計) | カーネルの `vixs-rtc` は評価ボードのDS1339(I2C `0xD0`)用で、この基板には無く読めない(`unable to read the hardware clock`)。時計は1970年から始まるので、`fake-hwclock`(最後に保存した時刻から再開)+ `ntpdate`(ネットワーク起動時に補正)で対処(`prepare_tree.sh` が標準で入れる) |
| パッケージ追加(apt) | wheezy は EOL。`archive.debian.org` に向け(`[trusted=yes]` と `Check-Valid-Until false`)で使える(`prepare_tree.sh` が設定) |
| UART / JTAG | 基板に信号が配線されていない |
| 公式の録画データの利用・DLNA配信・DTCP-IP | 純正アプリは動かさない。録画は別の録画ソフト側で行う前提。HDD登録情報 `.hai` は解読済みだが、録画DB(`00000015/` の `.dat`)の暗号は未解読で、既存録画の移行は未対応([docs/15](15_p3_structure_and_hai.md)) |
| ブートローダの差し替え | U-Boot / 4段目の差し替えは未実施(SPIの先頭1MBは難読化されており、書き込み時は難読化の適用が必要)。カーネル引数(`console=` など)は変えられない |
| Sony miniroot を使わない完全Debian化 | SPIのRFS(Sony miniroot)はまだ読み込まれる(`switch_root` で捨てられるだけ)。自前RFSは未作成 |

## 未解明・未検証

| 項目 | 状況 |
|---|---|
| ファーム(メディアエンジン)が起動後しばらくして `FW_HANGUP` になる | 原因不明。`rc.xcode4` の再読込で復活する(`nasne-recpt1` は開始時に確認して自動で再読込する)。I2Cのみ使う用途には影響しない |
| 復号ストリームを開いたまま強制終了するとnasneが固まることがある | 原因不明(pingは通りsshは応答せず、電源の抜き差しで復旧)。通常の終了(SIGTERM・接続切断)では起きない |
| ワンセグのサービスに復号ストリームを開くと、ドライバ内で戻らなくなる | **再現して特定**: ワンセグ(PMT PID 0x1FC8)に対して `OPEN_SECUREDTS` を開くと、`RECV` ioctl がD状態のまま戻らない(`SIGKILL`も効かない)。他のサービスは影響なし。nasne全体は応答し、`reboot -f` で復旧する。`nasne-recpt1` はワンセグを一覧に載せず、明示指定も404で拒否する。ファーム側の仕様かバグかは未解明 |
| 公式 `procmng` が止まる条件(PWR/REC赤点灯、LAN点灯、ping・ARPとも無応答) | procmng は検査に通らないと `/sbin/halt` を呼んで止まる(マネージャが不完全、`/dev/mtd0` が無い等で再現)。p3(録画領域)の初期構造(`.hai`、録画DBの雛形)が無いと、起動の約35秒後に本体が固まる(ネットワークも切れる。[docs/15](15_p3_structure_and_hai.md))。別件として、Debian直起動の機体から公式アプリを起動して固まる例は、p3の初期構造不足が原因の可能性が高い(`p3init` 後の再試験は未実施)。どの検査が決め手かは未特定。電源の入れ直しで戻る |
| MCUのステータス6バイト(末尾2バイトは「最後のコマンドからの経過(10ms単位)」、2バイト目の0x80はウォッチドッグ停止中)、電源・タイマ系コマンド | 一部判明。電源・タイマ系(`[0x02,..]` `[0x04,..]`)は未解読 |
| `/dev/mem` でI2Cレジスタを直接叩くとブロック0がNACKになる理由 | 未解明(HWミューテックスの絡みと推測)。**直接叩くとMCUのI2Cが固まる** |
| 復調IC / RFチューナーICの型番、どちらがISDB-T/Sか | 未確定 |
| バス0 `0x2a` のデバイス | 未確定(何を読んでも `00`) |

| ブートローダ内の `0x0` ブロックの表、ECC領域、SPI `0x90000` / `0xA0000` の blob | 未解読(鍵素材の可能性) |

## 作者側では検証不可(別の本体が必要なもの)

作者は CECH-ZNR2J を **1台しか持っていない**ため、次の項目は作者側では検証できません。別の本体をお持ちの方の確認結果(issue等)を歓迎します。

| 項目 | 内容 |
|---|---|
| 別の個体での動作全般 | HDD復旧手順(`phase1`→`read-id`→`final`→`p3init`)、`.hai` の生成、`00110022.dlm` の生成が、別の個体でも同じ結果になるか |
| 録画DBの雛形が個体IDに依存しないか | `p3init` が持つ雛形(121バイト)は、別のHDD2台で一致したことは確認済み。本体(個体ID)に依存するかは、本体が1台のため**不明** |
| 別のモデル(CECH-ZNR1J など) | 基板・チューナー構成・SPI配置が同じか |
| v2.60より古いファームがSPIに入っている本体 | SPIの内容・マネージャ生成・`final` との整合 |
| 古い公式ファーム(v1.00〜v2.5x)ごとの違い | SPI・マネージャ・起動の通しがバージョンごとにどう変わるか |
| 別の個体のHDDを付け替えたときの挙動 | `ChipID ERROR` で止まる負の対照(別IDのマネージャで確かに止まるか)、別本体への移植 |
| 個体差のあるハードウェア挙動 | チューナーの感度、`FW_HANGUP`、強制終了時の固まりなどが他の個体でも出るか |

## 作者側で検証できる(後日予定)

HDDは複数あるため、次は作者側で後日確認します。

- HDDの容量・メーカー違い(500GB・1TB・320GB 等)での復旧手順と直起動
- `phase1` から始めて `p3init` で完成させる**最初から続けた通し**
- SPIバックアップ `.dlm` の `--dest p3|both`、Debian直起動HDDでの動作
- Debian直起動の機体から公式アプリを一度だけ起動する試験(`p3init` で初期化したp3での再試験)
- 直起動の失敗時フォールバック(公式の起動経路)の実動作
- 長時間運用(ウォッチドッグ停止状態で数日)の安定性
- BS/CSの試験(BSが来ている入力での再試験)、tvheadend / EPGStation 連携、2つ目のチューナーの調査

## 動作確認した範囲

検証は CECH-ZNR2J の1台で、HDDは500GBのもの。ファームは v1.00 / v2.60。
他のモデル(CECH-ZNR1J など)や他のファーム版数での動作は未確認です。結果をissueで共有してもらえると助かります。

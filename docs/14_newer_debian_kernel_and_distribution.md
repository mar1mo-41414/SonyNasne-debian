# 14. Debian・カーネルを新しくできるか / 成果物を配布してよいか

> 技術的な見通しと、配布するときの考え方のメモ。**法的助言ではありません**(著作権の扱いは国や事情で変わります。不安なら専門家に相談してください)。

## 1. Debian を新しくできるか

結論: **今のカーネル(2.6.29)のままでは wheezy(7)が実質の上限**。

| Debian | glibc | 必要なカーネル | nasne(2.6.29)で |
|---|---|---|---|
| 7 wheezy | 2.13 | 2.6.x | ✅ 動く(このリポジトリ) |
| 8 jessie | 2.19 | 2.6.32 以上 | ❌ ld.so が「kernel too old」で止まる。glibc を `--enable-kernel` を下げて自前ビルドすれば動く**かもしれない**(未検証。新しいシステムコールを使うパッケージで次々に詰まる) |
| 9 stretch〜12 bookworm | 2.24〜2.36 | 3.2 以上 | ❌ 同上。さらに systemd が前提のパッケージが増え、systemd は 4.x 以降のカーネル機能を要求する |
| 13 trixie | 2.41 | 3.2 以上 | ❌ mipsel / mips64el は trixie で**公式アーキテクチャから外れた**([LWN](https://lwn.net/Articles/1033741)、Debian 13 のリリースノート)。bookworm(12)が最後 |

なので「Debianを新しく」は、事実上「**カーネルを新しくする**」とセットになる。それでも mipsel の最新は bookworm まで。

代替案: **musl ベースの小さなシステム**(Buildroot / OpenWrt など)なら、古いカーネルでも新しいユーザランド(新しいOpenSSH、busybox、各種ツール)を載せられる。
muslは必要なカーネルの要求が緩い。`nasne-recpt1` 自体は libc 不使用の静的バイナリなので、どのユーザランドでも動く。「パッケージを apt で足したい」ことが目的でなければ有力。

## 2. カーネルを新しくできるか

結論: **技術的には可能だが、大きな移植作業**になる。

- 今のカーネルは SIE が GPL で公開したベンダーの 2.6.29 で、SoC(ViXS XCode 4210 "Viper"、MIPS 74Kc)固有のコードは**メインラインに無い**:
  割り込み・タイマー等のプラットフォーム、SATA(`xcode-ahci`)、USB(`sduh-ehci`)、SPI(`xcode_spi`)、RTC(`vixs-rtc`)、Ethernet(SynopGMAC。メインラインには近い `stmmac` がある)。
  新しいカーネルでは Device Tree 化して、これらを移植または書き直す必要がある。
- さらに、チューナーを使うための `xcode4drv`(メディアエンジンのドライバ。ソースは GPL パッケージで公開されている)は、2.6.29 の内部APIに依存している。
  新しいカーネルに移すにはAPIの差(5.x/6.x では大きく変わっている)を埋める必要があり、中でファームウェア(バイナリ)を読み込む部分の挙動も確かめ直しになる。
- ブートローダ(U-Boot 1.1.3 + 4段目)は無改変のまま、展開後8MBまでのカーネルを物理 `0x10000000` に置いて `0xB0040000` へジャンプする形を維持できる。
  最小構成の新しいカーネルなら8MBに収まる見込みはあるが、カーネル引数(`console=` 等)は変えられない([docs/10](10_status_and_limits.md))。
- 現実的な段階: (a) 3.x/4.x LTS へ古いAPI互換を残したまま持ち上げる → (b) 起動(initramfs、Ethernet、SATA、USB)だけ新カーネルで動かす → (c) `xcode4drv` を移植、の順。(c) が山。

## 3. `00550066.dlm` とrootfsを GitHub Releases で配布してよいか

結論: **Sonyのファームウェアを含むものは配布しない。配布してよいのは「自分たちが書いたもの」と「再配布が許されているもの」だけ**。

| もの | 配布 | 理由 |
|---|---|---|
| 自作の `00550066.dlm`(`make_stage1_dlm.py` の出力) | ❌ **配布しない** | 中身が Sony の公式 rootfs(`procmng`、`dtvtuner` など Sony の著作物のバイナリを含む)そのもの + 差し替えた `rcS`。**二次的著作物**に当たる可能性が高い。embed モードはさらに Debian も束ねる |
| SPIのダンプ(ブートローダ等) | ❌ | Sony のファームウェアそのもの |
| 公式の `xcode4drv.ko` / `rc.xcode4` | ❌ | Sony のバイナリ(ソースがGPLで公開されていても、公式ファームに入っているビルド済みバイナリの再配布はこの限りではない)。`prepare_tree.sh` は**利用者の手元の公式ファームから取り出す**作りにしてある |
| 作成ツール(`make_stage1_dlm.py` など)、ドキュメント | ✅ | 自分で書いたもの(MIT)。利用者が自分で入手した公式ファームから、自分のPCで `.dlm` を作る |
| 自作カーネル(`knl_new.bin`) | ⚠️ 条件つきで可 | GPL v2 のカーネル(SIE公開のソース + 本リポジトリの差分)をビルドしたもの。配布するなら**対応するソース(取得スクリプト・差分・設定)を同じ場所に置く**必要がある。`build_knl.py` は 64バイトのヘッダの雛形だけをSonyのKNLから借りるが、ヘッダのフィールドは文書化済みで、雛形なしに作れる。外部ramdiskは含まない |
| Debian の rootfs(`prepare_tree.sh` が作るツリー) | ⚠️ 条件つきで可 | Debian の自由なソフトウェア。ただし GPL のバイナリを配るので、ソースへの案内(`archive.debian.org` / `snapshot.debian.org` のソースパッケージ)が必要。Sony のドライバ(上)は含めないこと。**それでも「ツリーを作るスクリプト」を配るほうがずっと単純** |

おすすめの配布物(Releases):
1. ツール一式のタグ付きスナップショット(ソースのみ)
2. (任意)自作カーネル `knl_new.bin` + `sha256` + ビルド手順とソースへのリンク(GPL対応)
3. **作らない**: `.dlm`、SPIダンプ、Sony のドライバ、ファームウェアの断片

補足:
- 公式ファームウェアは Sony の公開サーバから誰でも取得できる(手順内で `wget`)。利用者が自分でダウンロードして自分の機器にだけ使う形なら、配布者がSonyの著作物を再配布することにはならない。
- 機器のファームウェアを書き換えることは、メーカーの保証や利用規約の対象外になりうる。また地デジの受信機能は B-CAS カードを使う(復号はnasneのファームがカードと直接やり取りして行い、鍵やカードIDは取り出していない)。
  私的な視聴・録画の範囲で、自分の機器・自分のカードで使うこと。
- 日本の著作権法には、互換性確保のためのリバースエンジニアリング等に関する規定や、技術的保護手段の回避に関する規定がある。**本プロジェクトは保護の回避を目的としない**(録画データのDTCP-IPには触れない)が、配布物を増やすほど判断が難しくなるので、上の「配らない」方針がいちばん安全。

# 03. ファームウェア形式(`.dlm`)とHDDの「紐付け」

## `.dlm` ファイルの暗号

| 項目 | 内容 |
|---|---|
| 暗号 | **Blowfish の変種**(標準実装では復号できない) |
| 鍵 | 16バイト固定。miniroot の `init` バイナリの `.data` に**平文で埋め込まれている**(OTP・ハードウェア鍵とは無関係) |
| モード | CBC風チェイニング、IV = (0, 0) 固定 |
| 範囲 | 先頭64バイトのヘッダは必ず暗号化。ボディはヘッダの暗号化フラグが `1` のときだけ暗号化(それ以外は平文) |
| 実装 | [scripts/dlm_crypto.py](../scripts/dlm_crypto.py) |

標準Blowfishとの違い(実機の鍵スケジュールを逆アセンブルし、エミュレーションで1ワードずつ突き合わせて確認):

1. 鍵バイトを**符号付き**で読み(`lb`)、0x80以上のバイトは符号拡張してからP-arrayにXORする。
2. 鍵スケジュールの自己微分を始める前の S-box 初期状態が、標準の1024個の異なるπ定数ではなく、
   S[0]〜S[3] それぞれが「標準テーブル先頭4ワードのうち1つ」で256エントリすべて埋まった**縮退状態**。
3. ラウンド関数(F関数、18ラウンド)は標準どおり。

**ボディ末尾の8バイト未満の扱い**(実機の30MB超のrootfs、v2.60で確認): ボディ長が8の倍数+6バイトになる場合があり、
これを単純に切り捨てると、gzipトレーラ(CRC32/ISIZE)の一部を失って `tar`/`gzip` の展開が完結しない。
**直前のCBCブロック(暗号文)を再暗号化したキーストリームで末尾をXORする(CFB風)と、`tar -tvf`/`tar -xf` に正しく通る**ことを確認済み
(gzipトレーラのCRC32自体は一致しないままだが、tar本体の内容は正常。実機のストリーム処理(`FUN_00401ad0`)が本当にこの方式かは未確定で、
CRC32が合わない理由も未解明)。`dlm_crypto.py decrypt-body --tail cfb --inflate` で、トレーラ検証なしの生tarを取り出せる([docs/09](09_tools.md))。

## 64バイトヘッダ(復号後)

| offset | 長さ | 内容 | 検査 |
|---:|---:|---|---|
| 0x00 | 4 | マジック `"DLM\0"`(SPIのセグメントでは `KNL` `BKNL` `INFO` `INF2` `FMAP` など) | 一致必須 |
| 0x04 | 4 | セグメント全長(BE) | なし |
| 0x08 | 2 | **メジャーバージョン**(BE16)。v1.00 = 1、v2.60 = 2。`0` は特別扱い(後述) | `0` かどうかで分岐 |
| 0x0E | 1 | **ボディ暗号化フラグ**(1ならボディもBlowfish復号) | 分岐 |
| 0x0D | 1 | `0x10` ならgzip圧縮(SPIのKNL/RFSで使われる) | 分岐 |
| 0x10 | 4 | **hwtype**(BE)。SoCのシステム情報ページ `+0x10c` と一致必須 | 一致必須 |
| 0x14 | 32 | **日付文字列**(例 `Tue Oct 24 11:13:25 2017`) | マネージャの日付と一致必須(後述) |
| 0x3C | 4 | **CRC32**(BE) | 一致必須 |

**CRC32 の範囲**: 「CRC欄を0にしたヘッダ64バイト」→ 続けて「ファイルの残り全バイト(ボディ、暗号化されたまま)」を連続して `zlib.crc32` したもの。

ツール: `build_dlm.py`(構築・検証)、`ofw_tool.py`(公式パッケージの分解・ヘッダ書き換え)。使い方は [docs/09](09_tools.md)。

## 公式ファームパッケージの構造

`KRST3101_xxxx_SECURE.dlm`(Sonyの公開サーバから取得可)は3セグメントの連結:

```
KNL(SPIのKNLへ書くカーネル) ‖ RFS(SPIのRFSへ書くminiroot) ‖ DLM(HDD sys1の 00550066.dlm = rootfs)
```

`ofw_tool.py split` で分解できる。HDDのバンクディレクトリ内の `00220033.dlm` = KNL、`00440055.dlm` = RFS、`00550066.dlm` = DLM と、md5まで一致する
(ファーム更新処理がSPIの内容をHDDに写している)。

## sys1(p1)の構成

```
/disk0 (= sda1)
├─ 00110022.dlm   148B  マネージャ(HDDと本体の紐付け。下記)
├─ 00550066.dlm         現用rootfs(毎起動これからsys2を再構築)
├─ 009900AA.dlm    64B  現用rootfsヘッダの写し(initが書く。判定には使わない)
├─ 00CC00DD.dlm         更新/復元状態のフラグ
├─ 11002200/            Aバンク: 00110022 / 00220033(KNL) / 00440055(RFS) / 00550066(rootfs)
└─ 33004400/            Bバンク: 同上(旧版のrootfsとそれに対応するマネージャ)
```

## `00110022.dlm`(マネージャ)= HDDと本体の紐付け

**HDDと本体の「紐付け」の実体は、このファイルに書かれた本体の個体IDが、本体のSPI(INF2)の個体IDと一致するか、だけ。**
HDDのシリアル番号などは見ていない。

### 形式

```
[0:4]    CRC32(平文0x90バイト、zlib互換、リトルエンディアンで保存)
[4:148]  平文0x90バイトを、.dlm と同じ Blowfish-CBC(IV=0)で暗号化したもの
```

平文0x90バイト:

| offset | 内容 |
|---|---|
| 0x00–0x07 | **個体ID**。SPI INF2 本体 `+0x60` の8バイト |
| 0x08–0x0F | 不明(既存ファイルでは固定値。initは読まない) |
| 0x10–0x2F | rootfs(`00550066.dlm`)ヘッダ `+0x14` の日付文字列 |
| 0x30–0x4F | SPI の KNL セグメントヘッダ `+0x14` の日付 |
| 0x50–0x6F | SPI の RFS セグメントヘッダ `+0x14` の日付 |
| 0x70–0x8F | 不明(0x08–0x0F の4回繰り返し) |

`dlm_mng.py` は、実機のファイルを `decode` → `build` でバイト完全に再生成でき、さらに SPIダンプと rootfs `.dlm` の先頭64Bだけから
`from-spi` で生成した物が実機のファイルとバイト完全一致することを確認している。

### miniroot `init` が行う検査

1. `/disk0/00550066.dlm` のヘッダを復号し、hwtype を確認。
2. ヘッダ `+8`(メジャーバージョン)で分岐:
   - **`≠ 0`**(通常のファーム): マネージャの自動生成はしない。`/disk0/00110022.dlm` が必要。
   - **`== 0`**: `/disk0/00110022.dlm` が無い、またはサイズが148でなければ、**現在の本体の個体IDで新規生成**する
     (このとき生成されるファイルは不完全で、KNL/RFSの日付が空)。
3. `00110022.dlm` を読み、CRC32 が合わなければ `failed to read File`。
4. **個体ID照合**: `マネージャの[0:8] == 本体の個体ID` でなければ **`ChipID ERROR`**(失敗ループ)。
5. rootfs を読む際、マネージャ `+0x10` の日付と rootfs ヘッダの日付が一致しなければ `DLM date ERROR`(失敗ループ)。
6. すべて通れば sys2 を再構築して `switch_root`。

### HDDを復旧・移植する方法

| 方法 | 内容 | 検証状況 |
|---|---|---|
| ① マネージャを自作する | 個体IDが分かっていれば `dlm_mng.py from-spi` / `build` で作り、`/disk0/00110022.dlm` と各バンクdirの写しに置く | ファイル形式は実ファイルとバイト一致。実機で正常起動を確認 |
| ② ヘッダ `+8` を 0 にして本体に生成させる | rootfs の `+8` を 0 にしたものを置き、`00110022.dlm` を消して起動すると、本体のinitが個体IDを書き出す。それを読み出し、①で完全なマネージャを作る | 実機で個体IDの書き出しを確認 |

HDD全損機の復旧は ②→① を組み合わせて行う。手順: [docs/04](04_hdd_recovery_guide.md)。

### 実機での切り分け結果

公式 v2.60 の rootfs を使った3通り(自前ビルドのカーネルで起動):

| rootfs `+8` | マネージャ | 結果 |
|---|---|---|
| 0 に改変 | 無し(initが自動生成) | initの検査は通過するが、**起動後に固まる**(PWR/REC赤点灯、ネットワーク無応答)。自動生成のマネージャが不完全なため |
| 無改変(2) | 正規の完全なマネージャ | 正常起動(PWR点灯、WebUI表示) |
| 0 に改変 | 正規の完全なマネージャ | 正常起動 |

つまり **`+8 = 0` 自体は無害**で、問題は「自動生成されたマネージャが不完全」なこと。実用上は、個体IDを読み出して**完全なマネージャを自作して置く**。
公式 v1.00 / v2.60 のどちらも、自前ビルドのカーネルで丸ごと動く。

ネットで言われる「`00110022.dlm` は v1.00 のファームでしか再生成できない」という話は、**マネージャについては当てはまらない**(initの生成ロジックは新しいファームにも存在し、`dlm_mng.py`/`nasne_hdd_rebuild.py final` で、公式とバイト一致のものが作れる)。
ただし v1.00 には別の役目がある: **空のXFSのp3を初期化して公式アプリを起動させられるのは v1.00 だけで、v2.60 は止まる**([docs/04](04_hdd_recovery_guide.md))。以下は元の説明(
中身は SPI の情報と rootfs の日付だけで決まる)。

## 自作 `.dlm` で sys2 に任意のファイルを注入する(参考)

正しいヘッダ(マジック、hwtype、日付、CRC、暗号化フラグ=0)と、tar.gz のボディを持つ `.dlm` を `/disk0/00550066.dlm` に置くと、
起動のたびに任意の内容が sys2 に展開される(`build_dlm.py`)。初期の Debian chroot 起動はこれで行ったが、
現在は[直起動](05_kernel_and_direct_boot.md)に置き換えている。注意: 展開に失敗(tar失敗・容量不足・`/sbin/init` 不在)すると、
ヘッダ不正と同じ点滅ループに入り、HDD側からは原因を切り分けられない。
